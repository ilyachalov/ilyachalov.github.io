Я иногда провожу индивидуальные занятия для начинающих по программированию на языке C++. Недавно начал такие занятия для одного студента. После нескольких занятий он попросил посоветовать что-нибудь почитать по разработке программ с **_графическим_** интерфейсом на языке C++ для операционных систем **_Windows_**.

На самом деле, это не такая простая тема, как может показаться. Сам по себе синтаксически язык C++ достаточно универсальный для разных применений, в том числе для написания программ с графическим интерфейсом. Проблема здесь в том, что в этой области существует довольно много инструментов, но ни один из них не свободен от крупных недостатков. Поэтому при подборе инструмента для написания программ по вышеуказанным требованиям, думаю, придется изучить ряд инструментов, чтобы найти наиболее подходящий под конкретную задачу.

Я наметил для изучения по указанной теме три инструмента:
- [Windows API](https://ru.wikipedia.org/wiki/Windows_API);
- [фреймворк Qt](https://ru.wikipedia.org/wiki/Qt);
- фреймворк [WinUI 3](https://learn.microsoft.com/en-us/windows/apps/winui/winui3/).

Набор функций Windows API позволяет получить исполняемый файл маленького размера, программа получается быстрая и легко переносимая между разными версиями операционных систем Windows. Не требует специальных дополнительных инструментов по сравнению с написанием консольных программ. Недостатки: стиль кода устаревший ([легаси](https://ru.wikipedia.org/wiki/%D0%A3%D0%BD%D0%B0%D1%81%D0%BB%D0%B5%D0%B4%D0%BE%D0%B2%D0%B0%D0%BD%D0%BD%D0%B0%D1%8F_%D1%81%D0%B8%D1%81%D1%82%D0%B5%D0%BC%D0%B0)), для написания сложных интерфейсов может потребоваться писать много кода, почти нет современных книг на эту тему; не уверен, что существует современный визуальный редактор для создания графического интерфейса с Windows API. Однако, для учебных целей подоходит хорошо в том смысле, что дает понимание основ работы с окнами в операционной системе Windows.

Фреймворк Qt&nbsp;— наверное, самый популярный инструмент на сегодня в этой области. Кроссплатформенный, имеет открытый исходный код. Недостаток: достаточно большого размера исполняемый файл или небольшой исполняемый файл, требующий ряда динамических библиотек. Я с ним пока не работал, только почитал про него немного. Требует установки дополнительных инструментов по сравнению с написанием консольных приложений.

Описание фреймворка WinUI 3 в теории звучит очень интересно: рекомендуемый компанией Microsoft новый фреймворк для создания новых приложений для систем Windows (свежих версий Windows 10 и всех версий Windows 11) на настольных компьютерах для языков программирования C# и C++. Однако, на практике этот фреймворк очень трудно начать изучать, так как пока что документации именно по языку C++ практически нет. Почти всё, что есть на сайте Microsoft, заточено под язык C#, на который эта компания сегодня делает ставку. В такой ситуации язык C++ оказался в роли бедного родственника.

Я буду рассматривать (и при необходимости изучать) эти инструменты в указанном выше порядке и начну с Windows API.

## Windows API для графического интерфейса

Чтобы продемонстрировать создание графического интерфейса с Windows API, я написал две простых программы. (Я не оригинальный автор этих программ, они известны давно. Я просто немного их подправил в нужном мне стиле.)

Среди книг, которые обычно советуют почитать по этой теме, я выбрал книгу, которая чаще других попадалась мне в разных списках. Это книга «Технология программирования на C++. Win32 API-приложения» 2010 года издания от Николая Аркадьевича Литвиненко. Не могу сказать, что я в восторге от этой книги, но в ней много полезной информации по рассматриваемой теме. Книгу легко найти в интернете.

Первая программа просто выводит диалоговое окно с текстовым сообщением. Вот как результат ее работы выглядит у меня на компьютере с операционной системой Windows 10:

![](/images/message-box-winapi.png){:style="display:block; margin-left:auto; margin-right:auto;}

Исходный код программы я пишу ([https://utf8everywhere.org](https://utf8everywhere.org)) в кодировке UTF-8 (без [BOM](https://ru.wikipedia.org/wiki/%D0%9C%D0%B0%D1%80%D0%BA%D0%B5%D1%80_%D0%BF%D0%BE%D1%81%D0%BB%D0%B5%D0%B4%D0%BE%D0%B2%D0%B0%D1%82%D0%B5%D0%BB%D1%8C%D0%BD%D0%BE%D1%81%D1%82%D0%B8_%D0%B1%D0%B0%D0%B9%D1%82%D0%BE%D0%B2)). Чтобы протестировать возможности Windows API для этой кодировки, я специально ввел в текстовое сообщение в окне кроме английских букв русские буквы, китайские иероглифы и эмодзи. Эмодзи, к сожалению, выводятся в черно-белом виде, но это простительная мелочь.

Также мне не нравится, что шрифт довольно мелкий. Но, насколько я знаю, функция [MessageBox](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-messagebox) из Windows API, которую я здесь использую, не позволяет регулировать размер шрифта в этом окошке. Для таких вещей нужно писать своё окно, создание которого будет продемонстрировано во второй программе в этом посте.

Функция `MessageBox` позволяет выводить в это окно многострочный текст, показывать или не показывать иконку слева от текста, выбирать для иконки разные изображения из фиксированного списка, задавать разные наборы кнопок из фиксированного списка.

Исходный код первой программы:

```cpp
// Исходный код этой программы написан в кодировке UTF-8 (без BOM).
// При компиляции из командной строки с помощью MSVC (cl.exe) используйте
// параметр "/utf-8".

#define UNICODE
#include <windows.h>

#pragma comment(lib, "user32.lib") // для MessageBox

int APIENTRY WinMain(HINSTANCE hInstance, HINSTANCE hPrevInstance,
                     LPSTR lpCmdLine, int nCmdShow)
{
    MessageBox(NULL,

        L"Hello, world!\n"
        "Простая программа с графическим интерфейсом!\n"
        "Приветствие по-китайски: 你好!\n"
        "Эмодзи: 😂🤣🧐😱😲",

        L"Приложение с GUI на WinAPI",
        MB_OK | MB_ICONINFORMATION);

    return 0;
}
```

Для функций Windows API обычно включают заголовочный файл `windows.h`. Кроме этого, компилятору нужно указать библиотеку, в которой хранится код используемой функции. Здесь я указал библиотеку `user32.lib` прямо в коде с помощью директивы препроцессора `#pragma`. Код может быть успешно скомпилирован без этой директивы препроцессора, но в таком случае понадобится указать нужную библиотеку в соответствующем параметре компилятора при его запуске из командной строки.

Я использую компилятор [MSVC](https://ru.wikipedia.org/wiki/Microsoft_Visual_C%2B%2B) (cl.exe), который устанавливается автоматически в рамках установки рабочей нагрузки «Desktop development with C++» (по-русски «Разработка классических приложений на C++») для интегрированной среды разработки «Visual Studio Community 2022». (Установка этого компилятора [возможна](https://learn.microsoft.com/en-us/cpp/build/building-on-the-command-line) и без интегрированной среды разработки «Visual Studio», но я не пользуюсь этим методом.)

Вот команда, которую я использовал для компиляции программ из этого поста в командной строке [cmd.exe](https://ru.wikipedia.org/wiki/Cmd.exe):

```
cl /utf-8 program.cpp
```

При работе с функциями Windows API придется привыкнуть к использованию множества макросов и предопределенных констант, имена которых определены в верхнем регистре. Например, в коде выше используются константы `MB_OK` и `MB_ICONINFORMATION`, которые определяют набор кнопок и вид иконки в выводимом окне. Возможные названия констант для настройки внешнего вида окна следует смотреть в документации к используемой функции.

В программах с графическим интерфейсом в операционных системах Windows для языка C++ в качестве точки входа обычно вместо функции `main` используют функцию [`WinMain`](https://learn.microsoft.com/en-us/windows/win32/learnwin32/winmain--the-application-entry-point).

Обратите особое внимание на определение макроса `UNICODE` в начале программы. Это определение должно находиться до включения каких-либо заголовочных файлов в программу.

В наборе функций Windows API обычно функции, как-либо работающие с текстом, предоставляются в двух версиях: с буквой `A` (для текста в однобайтных кодировках) в конце названия и с буквой `W` (для текста в многобайтных кодировках) в конце названия. Например, на самом деле функции `MessageBox`, которую я использую в программе выше, не существует. Есть функции `MessageBoxA` и `MessageBoxW`, их можно использовать напрямую. Однако, для удобства придумали писать просто соответствующее название без буквы, а компилятор сам решит, какую из двух имеющихся функций выбрать. Выбор компилятора зависит от определения в программе макроса `UNICODE`: если он определен, компилятор выберет функцию `MessageBoxW`, иначе будет выбрана функция `MessageBoxA`.

## Программа с Windows API с пользовательским окном

В предыдущей программе было использовано одно из предопределенных окон систем Windows. Такие окна предназначены для своих конкретных областей использования и не предполагают каких-то больших изменений во внешнем виде или добавления какого-либо функционала.

Во второй программе показан классический способ создания окон в программах с Windows API. Такие окна тоже имеют определенные ограничения на изменение внешнего вида, но предоставляют довольно длинный список возможностей, которых обычно достаточно для реализации всех нужд, которые могут понадобиться пользователям и программистам в графическом интерфейсе программы.

Программа выводит пустое окно, на которое в дальнейшем можно добавить нужные элементы интерфейса вроде меню, текстовых полей, кнопок и других элементов управления. Также это окно можно сделать родительским для других окон приложения. Полученное окно можно сворачивать, разворачивать и закрывать. Также можно с помощью мыши менять его размеры и перемещать по экрану.

Вот как такое окно выглядит у меня на компьютере с операционной системой Windows 10:

![](/images/first-window-winapi.png)

Приведенная выше картинка имеет оригинальные размеры 786&nbsp;×&nbsp;393 пикселей. Однако, в программе я задал размеры окна в 800&nbsp;×&nbsp;400 пикселей. Почему получается разница?

При переходе на Windows 10 дизайнеры компании Microsoft сделали дизайн окон «плоским», визуально убрав толстые боковые и нижнюю границы рамки окна. Но в действительности эти границы рамки окна не убрали, а просто сделали прозрачными. Причина в том, что тонкие границы сложно «зацепить» мышью для изменения размеров окна, поэтому границы рамки остались, но сделались невидимыми.

Ширина невидимой части границ рамки составляет 7 пикселей. Поэтому ширина видимой части окна уменьшена на 14 пикселей (по 7 пикселей слева и справа), а высота видимой части окна уменьшена на 7 пикселей (только снизу, так как сверху дизайнеры ничего не меняли, там остался достаточно широкий заголовок окна, за который легко «зацепить» мышью).

Исходный код второй программы:

```cpp
// Исходный код этой программы написан в кодировке UTF-8 (без BOM).
// При компиляции из командной строки с помощью MSVC (cl.exe) используйте
// параметр "/utf-8".

#define UNICODE
#include <windows.h>

#pragma comment(lib, "user32.lib") // для разных функций WinAPI
#pragma comment(lib, "gdi32.lib")  // для CreateSolidBrush

LRESULT CALLBACK WndProc(HWND, UINT, WPARAM, LPARAM); // прототип

// точка входа
int APIENTRY WinMain(HINSTANCE hInstance, HINSTANCE hPrevInstance,
                     LPSTR lpCmdLine, int nCmdShow)
{
    LPCWSTR CLASS_NAME = L"MainWindow";

    // 1. Создание и регистрация класса окна
    WNDCLASS wc{};
    wc.hInstance = hInstance;
    wc.lpfnWndProc = WndProc;
    wc.lpszClassName = CLASS_NAME;
    wc.hbrBackground = CreateSolidBrush(RGB(230, 230, 230));
    RegisterClass(&wc);

    // 2. Создание окна и показ его на экране
    HWND hwnd{};
    hwnd = CreateWindowEx(0, CLASS_NAME, L"Моё первое окно с WinAPI",
        WS_OVERLAPPEDWINDOW, CW_USEDEFAULT, CW_USEDEFAULT, 800, 400,
        NULL, NULL, hInstance, NULL);
    if (hwnd == NULL) return 0;
    ShowWindow(hwnd, nCmdShow);

    // 3. Цикл обработки сообщений
    MSG msg{};
    while (GetMessage(&msg, NULL, 0, 0))
    {
        TranslateMessage(&msg);
        DispatchMessage(&msg);
    }

    return 0;
}

// функция окна для обработки сообщений
LRESULT CALLBACK WndProc(HWND hwnd, UINT uMsg, WPARAM wParam, LPARAM lParam)
{
    switch (uMsg)
    {
        case WM_DESTROY:
            PostQuitMessage(0);
            return 0;
        default:
            return DefWindowProc(hwnd, uMsg, wParam, lParam);
    }
}
```

В операционных системах Windows при создании нового окна его тип (класс) должен быть зарегистрирован, если этот тип новый (в нашем случае мы как раз создаем окно своего типа, то есть типа, который является новым для операционной системы).

При создании каждого нового окна операционная система назначает ему в качестве идентификатора целое число, которое называют **_дескриптором_** (описателем окна), по-английски handle или window handle, сокращенно HWND. Дескриптор окна требуется для выполнения любых манипуляций с этим окном. В принципе, с помощью дескриптора окна из своего приложения можно манипулировать любым окном любого чужого приложения, если это явно не запрещено программистом чужого приложения. В большинстве приложений, в том числе системных, это не запрещено.

Управление окнами и взаимодействие окон внутри операционных систем Windows происходит с помощью отправки и получения сообщений (message). Разных типов сообщений существует довольно много. Например, в программе выше в коде функции WndProc используется сообщение, обозначенное константой `WM_DESTROY`. Как только наше окно получит это сообщение, оно закроется и работа приложения завершится.

При создании класса окна в свойство `lpfnWndProc` класса нужно записать указатель на функцию, которая будет обрабатывать сообщения, приходящие нашему окну. В коде выше это функция `WndProc` (ее название может быть любым). Как только операционная система получит сообщение для нашего окна, она вызовет эту функцию для обработки полученного сообщения. В программировании функции, передаваемые какому-либо коду для обработки некоего события, традиционно называют «функциями обратного вызова», по-английски callback. В данном случае функция WndProc и является функцией обратного вызова.

Мне не понравился цвет по умолчанию клиентской части создаваемого окна, так как он сливался с цветом заголовка окна и не было видно границы между клиентской частью окна и заголовком окна. Поэтому я создал кисть темно-серого цвета `RGB(230, 230, 230)` с помощью функции `CreateSolidBrush` и покрасил ею фон клиентской части окна. Это можно сделать, записав полученную кисть в свойство `hbrBackground` класса окна.

Поскольку функция `CreateSolidBrush` определена в библиотеке `gdi32.lib`, пришлось подключить эту библиотеку при компиляции программы с помощью директивы препроцессора `#pragma`.
